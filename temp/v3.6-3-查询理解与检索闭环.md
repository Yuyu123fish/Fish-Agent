# v3.6-3 查询理解与检索闭环（Query Understanding & Quality Tracking）

> 版本线：v3.6 Phase 3
> 改动范围：Java 后端 `rag/pipeline/` + `memory/longterm/` + 新增 RAG 日志组件
> 依赖：v3.4 Reranker + v3.5 精切已完成
> 前置条件：v3.5 已完成并验证

---

## 一、解决什么问题

### 问题 1：查询扩展只是词级拆解，不是语义扩展

当前 `RagQueryExpand.java` 按词边界分词，把用户原句拆成 token 片段作为子查询。

**问题**：
- 不是真正的"多查询扩展"——只是把句子拆成词
- 举例：用户问"怎么用 Docker Compose 部署 Spring Boot"，当前扩展出 `"Docker" / "Compose" / "部署" / "Spring" / "Boot"` 这些孤立词
- 而真正需要的是语义层面的变体：`"Docker Compose 部署 Java 应用的最佳实践"` / `"Spring Boot 项目容器化部署步骤"`
- 孤立词作为子查询去检索，匹配到的都是恰好包含这些词的文档，缺乏上下文

**表现**：复杂多意图查询（"之前聊的 Redis 配置和 Docker 部署再讲一下"）检索效果差——系统无法理解用户实际要搜什么。

### 问题 2：长期事实写入不查重

当前 `LongTermMemoryIngestionService` 每轮对话结束后异步抽取事实 → ES 写入，不做去重。

**问题**：
- 用户多轮对话中反复提到同一事实（如"我是做 Java 后端的"、"我在做微服务项目"），每轮都抽取并存入 ES
- 检索时这些重复事实占据 Top-K 名额，挤掉其他有用信息
- 随着对话增多，ES 中冗余事实不断累积

**表现**：检索"项目相关"时 Top-8 里有 4 条都是同一事实的不同表述。

### 问题 3：没有检索质量可观测性

当前 RAG 检索结果注入后，模型用不用、用户满不满意，完全没有追踪。

**问题**：
- 不知道当前参数（8 facts / 4000 chars / 512 token chunk / 50 overlap）是否合理
- 不知道哪些查询检索效果差，无法针对性优化
- 优化了 Reranker / 分块后没有量化指标验证效果

**表现**：RAG 是黑盒——改了参数只能靠主观感受评估效果。

## 二、方案设计

### 2.1 整体架构变化

```
改动前（v3.5）：
  用户消息 → [可选重写] → [词级扩展] → 三路检索 → RRF → Rerank → 注入

改动后（v3.6）：
  用户消息 → [可选重写] → [LLM 语义查询分解] ← 重写
                                 ↓
                        三路检索 → RRF → Rerank → 注入
                                 ↓
                          RAG 质量日志记录 ← 新增

  长期事实抽取 → embedding 查重 → 相似度 > 阈值则跳过 ← 新增
```

### 2.2 新增/修改组件

| 组件 | 类型 | 职责 |
|------|------|------|
| `RagQueryExpand.java` | **重写** | 从词级拆解改为 LLM 驱动的语义查询分解 |
| `RagQueryDecomposer` | 新增（可选替代方案） | HyDE：生成假设性答案的 embedding 去检索 |
| `LongTermMemoryIngestionService.java` | 修改 | 写入前 embedding 余弦查重 |
| `LongTermMemoryDeduplicator` | 新增 | embedding 相似度去重逻辑 |
| `RagQualityLogger` | 新增 | 记录每次 RAG 检索的全链路指标 |

## 三、方案详解

### 3.1 LLM 语义查询扩展（RagQueryExpand 重写）

**选型对比**：

| 方案 | 查询质量 | 额外延迟 | 额外 LLM 调用 | 实现复杂度 |
|------|---------|---------|-------------|-----------|
| 词级拆解（当前） | 低 | 0 | 0 | 低 |
| LLM 查询分解（推荐） | 高 | +0.5~2s | 1 次 | 中 |
| HyDE（假设性文档） | 很高 | +1~3s | 1 次 | 中 |
| LLM 分解 + HyDE 组合 | 最高 | +2~4s | 2 次 | 高 |

**选择 LLM 查询分解的理由**：
- 1 次 LLM 调用即可生成 2~4 条语义不同的子查询，延迟可接受
- 与现有 `memoryChatModel`（独立 LLM 实例）共用，不占主模型资源
- HyDE 作为可选增强项，可以在基础版验证效果后再叠加

**LLM 查询分解 Prompt 设计**：

```
你是一个搜索查询优化专家。给定用户的问题，将其拆解为 2~4 个不同角度的搜索查询。

规则：
1. 每条子查询应该是完整、具体的检索句，不是关键词堆砌
2. 覆盖用户问题的不同意图维度
3. 如果用户问题只有一个明确意图，保留原句即可，不要强行拆分
4. 输出严格的 JSON 数组格式

示例：
用户问题："之前聊的 Docker 部署和 Redis 持久化再讲一下"
输出：["Docker 容器部署应用的最佳实践", "Redis 持久化机制 RDB 和 AOF 详解"]

用户问题："今天天气怎么样"
输出：["今天天气怎么样"]

现在请处理以下用户问题：
"{user_message}"

输出：
```

**实现要点**：

```
RagQueryExpand.expand(query: String) → List<String>:

  1. 调用 memoryChatModel，传入上述 prompt
  2. 解析 LLM 返回的 JSON 数组
  3. 校验：每个子查询长度 5~200 字符，总数 ≤ max-sub-queries（默认 12）
  4. 失败降级：LLM 超时/解析失败 → 回退到原 query 单条检索

配置：
  fish.rag.expand.enabled       = true    （总开关）
  fish.rag.expand.max-queries   = 4       （最多生成几条子查询）
  fish.rag.expand.temperature   = 0.3     （LLM 采样温度，偏低保证稳定）
  fish.rag.expand.timeout-ms    = 3000    （超时降级阈值）
```

**与现有查询扩展的关系**：
- 替换掉现有的词级拆解逻辑（`RagQueryExpand` 原实现）
- 保留 `expand.enabled` 开关，关闭时回退到原 query 单条检索（不是词级拆解）
- 如果需要保留词级拆解作为降级方案，可增加 `expand.strategy=llm|token|identity` 三档

### 3.2 HyDE 假设性文档嵌入（可选增强）

**原理**：先用 LLM 生成一个"假设性答案"，再用这个答案的 embedding 去检索。因为答案的语义比问题更接近目标文档，检索效果通常更好。

**示例**：
```
用户问题："Docker Compose 怎么配置"
假设性答案（LLM 生成）：
  "Docker Compose 配置使用 YAML 格式的 docker-compose.yml 文件。
   基本结构包含 version、services、networks、volumes 四个顶级键..."
用这段答案的 embedding 去检索 → 更容易命中包含实际配置步骤的文档
```

**实现**：

```
HyDE 流程（可选，默认关闭）：
  1. 用户 query → LLM 生成假设性答案（200~500 字）
  2. 假设性答案 → DashScope embedding → 向量
  3. 用这个向量（而非 query 的向量）去做 knn 检索
  4. 文本路仍用原始 query

配置：
  fish.rag.hyde.enabled       = false   （默认关闭）
  fish.rag.hyde.max-tokens    = 300     （假设性答案最大 token 数）
  fish.rag.hyde.temperature   = 0.5     （稍微高一些，生成更自然的答案）
```

**为什么默认关闭**：
- HyDE 对事实型查询效果好，但对闲聊型查询（"你好"/"帮我写个代码"）反而有害——LLM 生成的不相关假设答案会误导检索
- 需要先在 LLM 查询分解的基础上验证效果，再考虑叠加 HyDE

### 3.3 长期事实 embedding 查重（LongTermMemoryDeduplicator）

**选型对比**：

| 方案 | 去重效果 | 实时性 | 额外开销 |
|------|---------|--------|---------|
| 精确文本匹配（当前无） | 差（同义不同词无法识别） | — | 零 |
| embedding 余弦相似度（推荐） | 好（语义级去重） | 高（实时计算） | 每次抽取多 1 次 ES knn 查询 |
| LLM 判断是否重复 | 最好 | 低（多 1 次 LLM 调用） | 延迟 +1~2s |

**选择 embedding 余弦相似度的理由**：
- 成本低——只需对抽取的新事实做一次 embedding，然后 ES knn 搜索自身索引比对
- 准确度够用——余弦 >0.92 基本能覆盖同义重复
- 不增加 LLM 调用（长期事实抽取本身就要做 embedding 写入 ES，复用这个 embedding 即可）

**实现**：

```
LongTermMemoryIngestionService.ingestFromUserInput():

  现有流程：
    1. LLM 抽取事实列表 → facts: List<String>
    2. 逐条写入 ES

  新增去重步骤（在步骤 1 和 2 之间）：
    1.5. 对每条 fact:
      a. 生成 embedding（复用现有 embedder）
      b. ES knn 搜索 fish-user-memory：
         knn(field="embedding", vector=fact_embedding, k=3)
         filter: user_id = currentUser
      c. 如果 Top-1 结果的 cosine > 0.92 → 判定为重复，跳过
      d. 否则 → 写入 ES

  配置：
    fish.memory.dedup.enabled         = true
    fish.memory.dedup.similarity-threshold = 0.92
```

**ES knn 查重查询示例**：

```json
{
  "knn": {
    "field": "embedding",
    "query_vector": [0.1, 0.2, ...],
    "k": 3,
    "num_candidates": 20
  },
  "query": {
    "term": { "user_id": "12345" }
  },
  "_source": ["content"],
  "size": 3
}
```

### 3.4 检索质量追踪（RagQualityLogger）

**设计目标**：不侵入业务逻辑，以观察者模式记录 RAG 全链路指标，供后续分析和调优。

**记录内容**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `trace_id` | String | 每次对话的唯一标识（= sessionId + turnNumber） |
| `user_id` | String | 用户 ID |
| `session_id` | String | 会话 ID |
| `original_query` | String | 用户原始输入 |
| `rewritten_query` | String? | 重写后的查询（如有） |
| `expanded_queries` | List\<String\> | 扩展后的子查询列表 |
| `recall_total_hits` | int | 初检索总命中数（去重前） |
| `recall_deduped_hits` | int | 去重后命中数 |
| `fusion_top_n` | int | RRF 融合后保留数 |
| `rerank_input_count` | int | 喂给 Reranker 的候选数 |
| `rerank_top_score` | float | Reranker 最高分 |
| `rerank_lowest_score` | float | Reranker 最低分（注入的最后一条） |
| `injected_fact_count` | int | 最终注入的事实条数 |
| `injected_total_chars` | int | 注入内容总字符数 |
| `recall_latency_ms` | long | 初检索耗时 |
| `rerank_latency_ms` | long | Rerank 耗时 |
| `total_latency_ms` | long | RAG 全链路耗时 |

**存储选型**：

| 方案 | 查询能力 | 部署成本 | 适用场景 |
|------|---------|---------|---------|
| MySQL 新表 | 中（SQL 查询） | 零（已有 MySQL） | 数据量可控，简单聚合 |
| ES 新索引 | 高（全文+聚合） | 零（已有 ES） | 推荐方案——天然适合日志分析 |
| 日志文件（JSON Lines） | 低（需外部工具） | 零 | 开发调试阶段 |

**选择 ES 新索引**：
- 项目已有 ES 基础设施，零额外部署
- ES 的聚合查询天然适合"按天统计平均命中数""按用户统计检索失败率"等分析场景
- 不增加 MySQL 负担

**ES 索引 mapping**：

```json
{
  "fish-rag-trace": {
    "mappings": {
      "properties": {
        "trace_id":       { "type": "keyword" },
        "user_id":        { "type": "keyword" },
        "session_id":     { "type": "keyword" },
        "original_query": { "type": "text", "analyzer": "ik_max_word" },
        "expanded_queries": { "type": "text", "analyzer": "ik_max_word" },
        "recall_total_hits":   { "type": "integer" },
        "recall_deduped_hits": { "type": "integer" },
        "fusion_top_n":        { "type": "integer" },
        "rerank_input_count":  { "type": "integer" },
        "rerank_top_score":    { "type": "float" },
        "rerank_lowest_score": { "type": "float" },
        "injected_fact_count": { "type": "integer" },
        "injected_total_chars": { "type": "integer" },
        "recall_latency_ms":   { "type": "long" },
        "rerank_latency_ms":   { "type": "long" },
        "total_latency_ms":    { "type": "long" },
        "created_at":          { "type": "date", "format": "epoch_millis" }
      }
    }
  }
}
```

**写入方式**：异步写入（`CompletableFuture.runAsync()`），不阻塞对话主流程。写入失败仅记 WARN 日志。

**配置**：

| 配置 | 默认值 | 说明 |
|------|--------|------|
| `fish.rag.tracing.enabled` | `true` | 质量追踪开关 |
| `fish.rag.tracing.index-name` | `fish-rag-trace` | ES 索引名 |
| `fish.rag.tracing.async` | `true` | 异步写入 |
| `fish.rag.tracing.sample-rate` | `1.0` | 采样率（0.0~1.0，1.0 = 全量记录） |

## 五、面试叙事

> "初版查询扩展只是按词边界拆解成孤立关键词，多意图查询检索效果差。
> v3.6 改为 **LLM 驱动的语义查询分解**——用独立模型将用户问题拆成 2~4 个不同角度的完整检索句，
> 覆盖多意图场景。长期事实写入前用 **embedding 余弦相似度查重**（>0.92 判定为重复跳过），
> 避免冗余事实占 Top-K 名额。新增 **RAG 全链路质量追踪**——每次检索记录 query/子查询/命中数/
> rerank 分数/延迟等指标写入 ES，实现数据驱动的检索参数调优。"

## 六、验收标准

1. `fish.rag.expand.enabled=false` 时行为与 v3.5 完全一致（兼容回归）
2. LLM 查询分解生成 1~4 条语义不同的子查询，失败时自动降级到原 query
3. 长期事实写入前做 embedding 查重，相似度 >0.92 的事实不重复写入
4. `fish.rag.tracing.enabled=true` 时每次 RAG 检索异步写入 `fish-rag-trace` 索引
5. 追踪数据包含完整的延迟分解（recall / rerank / total）
6. HyDE 功能 `fish.rag.hyde.enabled=false` 时不影响任何现有行为

## 七、已知风险与缓解

| 风险 | 缓解措施 |
|------|---------|
| LLM 查询分解增加 0.5~2s 延迟 | 使用独立的 `memoryChatModel` 不占主模型；超时 3s 自动降级；可关闭 |
| 查询分解对简单查询过度拆分 | Prompt 约束"单意图问题保留原句"；最少 1 条、最多 4 条 |
| embedding 查重增加 ES knn 查询开销 | k=3、num_candidates=20，每次查重 <10ms；异步执行不阻塞 |
| HyDE 对闲聊型查询有副作用 | 默认关闭，开启后只替换向量路的 query，文本路不变 |
| 追踪日志写入量可能较大 | 采样率可配置；异步写入；ES ILM 策略自动清理 30 天以上数据 |
