# v3.5-2 知识加工精切（Structured Chunking & PDF Hybrid）

> 版本线：v3.5 Phase 2
> 改动范围：Python Worker（`parser/` + `chunker/` + `storage/elasticsearch.py`）+ ES mapping DDL
> 依赖：v3.4 Reranker 已上线（原料质量提升后 Reranker 效果放大）
> 前置条件：v3.4 已完成并验证

---

## 一、解决什么问题

### 问题 1：固定 token 滑窗在句子/段落中间硬切

当前 `text_chunker.py` 用 tiktoken `cl100k_base` 编码器，512 token 硬切 + 50 token overlap。

**问题**：
- 完全无视文档的自然结构（标题、段落、表格、列表），在句子中间、表格中间硬切
- 例如："Redis 的持久化机制包括两种方式：第一种是 RDB 快照，第二种是" → chunk N 结束；"AOF 追加日志，各自有不同的适用场景" → chunk N+1 开始。50 token overlap 不一定覆盖这个断点
- 对不同类型文档（表格 xlsx、幻灯片 pptx、学术论文 PDF）用同一套参数——表格被切碎后行列关系丢失

**表现**：用户上传一份包含技术参数表的 xlsx，检索时只能命中零散的单元格，无法理解完整的行记录。

### 问题 2：文字型 PDF 被强行 OCR

当前所有 PDF 统一走 PyMuPDF 渲染 → Tesseract OCR（300 DPI）。

**问题**：
- 文字型 PDF（LaTeX 论文、Word 导出 PDF）本可以直接提取文本，准确率 100%，耗时毫秒级
- 被强行 OCR 后准确率降到 ~95%，耗时增加 10~100 倍
- v3.3 的 OCR 清洗管道能补救一部分，但源头用 OCR 就是浪费

**表现**：用户上传一份 50 页的文字型 PDF，Worker 处理耗时 3~5 分钟（全部 OCR），而直接文本提取只需 2~3 秒。

### 问题 3：ES 文档缺少关键元数据

当前 ES 索引只有 `content` + `embedding` + `doc_id` + `page_number` + `chunk_index`。

**缺失**：
- 没有 `doc_name`——检索结果不知道来自哪个文档，无法做按文档过滤
- 没有 `file_type`——无法按文档类型加权或过滤
- 没有 `token_count`——无法判断 chunk 的质量和完整性
- 没有 `created_at` 的时间衰减——3 年前的文档和今天的文档权重相同

**表现**：Reranker 精排时无法利用文档来源、类型等元数据做加权；质量追踪缺少数据基础。

## 二、方案设计

### 2.1 整体架构变化

```
改动前（v3.4）：
  Parser.parse() → list[RawElement]
                          ↓
            text_chunker（固定 512 token 滑窗）
                          ↓
               embedder → ES bulk

改动后（v3.5）：
  Parser.parse() → list[RawElement]
                          ↓
  StructuredChunker（按 element_type 差异化分块策略）← 新增
    ├─ Text → 语义滑窗（句子边界对齐）
    ├─ Table → 整表为一个 chunk / 按行组切分
    ├─ Title → 与后续 Text 合并，不做独立 chunk
    └─ 混合结构 → 按结构边界切分 + overlap 保留上下文
                          ↓
               embedder → ES bulk（携带新增元数据字段）
```

PDF 解析流程变化：

```
改动前（v3.4）：
  PyMuPDF 渲染 300 DPI → Tesseract OCR → 清洗 → 分块

改动后（v3.5）：
  PyMuPDF 直接提取文本 → 检测质量（长度/CID/乱码比例）
    ├─ 质量合格 → 文本清洗 → 分块（毫秒级）
    └─ 质量不合格 → 渲染 300 DPI → Tesseract OCR → 清洗 → 分块（秒级）
```

## 三、方案详解

### 3.1 结构化分块（StructuredChunker）

**设计原则**：不再无脑 512 token 滑窗，而是根据 `RawElement.element_type` 选择不同分块策略。

**选型对比**：

| 方案 | 精度 | 复杂度 | 适用场景 |
|------|------|--------|---------|
| 固定 token 滑窗（当前） | 低（无视结构） | 最低 | 纯文本无结构 |
| 按文档结构边界切分（推荐） | 高（保留语义完整性） | 中 | 有结构的文档（docx/html/pptx） |
| 语义分块（embedding 相似度） | 最高 | 高（额外 embedding 开销） | 长篇无结构文本 |

**选择按文档结构边界切分的理由**：
- docx 有标题层级、html 有 DOM 标签、pptx 有幻灯片边界——这些都是天然的语义边界，不需要额外计算
- 不增加 embedding 开销（语义分块需要先对每个句子算 embedding）
- 实现复杂度适中，且与现有 `RawElement` 的 `element_type` 字段天然对齐

**分块策略矩阵**：

| element_type | 分块策略 | 说明 |
|-------------|---------|------|
| `Text` | 句子边界对齐的 token 滑窗 | 在句号/问号/感叹号处对齐切分，不再硬切句子中间 |
| `Title` | **与后续 Text 合并** | 标题不独立成 chunk，而是与紧跟的段落合并，保留"标题→内容"的语义关联 |
| `Table` | **整表为一个 chunk**（≤1024 token）或 **按行组切分**（>1024 token） | 表格的行列关系是核心语义，不能切碎 |
| 混合（Title + Text） | 按结构边界（Title 位置）切分为大块，再按 token 限制细分 | docx 的"章节→段落"结构完美匹配 |

**关键实现细节**：

```
StructuredChunker.chunk(elements: list[RawElement]) → list[ChunkResult]:

  Step 1: 结构合并
    - 将 Title 与紧跟的 Text 合并为一个 Section
    - 保留 Table 的完整性

  Step 2: 按类型分块
    - Section（Title + Text）→ 按 token 限制（默认 512）在句子边界对齐切分
    - Table → 如果整表 ≤ 1024 token 则保留完整；否则按行组切分，每组保留表头
    - 独立 Text → 按 token 限制在句子边界对齐切分

  Step 3: overlap 处理
    - 相邻 chunk 之间保留 1~2 个句子的 overlap（约 50 token）
    - Table 分块时在每块开头重复表头行

  Step 4: 元数据携带
    - 每个 chunk 记录 source_element_type、page_number、section_title
```

**配置项**：

| 配置 | 默认值 | 说明 |
|------|--------|------|
| `FISH_WORKER_CHUNK_SIZE` | `512` | 最大 token 数（保持不变） |
| `FISH_WORKER_CHUNK_OVERLAP` | `50` | overlap token 数（保持不变） |
| `FISH_WORKER_TABLE_MAX_TOKENS` | `1024` | 表格独立 chunk 的最大 token 数 |
| `FISH_WORKER_CHUNK_STRATEGY` | `structured` | `structured`（新）或 `flat`（兼容旧版） |

### 3.2 PDF 混合提取策略

**选型对比**：

| 方案 | 文字型 PDF | 扫描件 PDF | 速度 | 准确率 |
|------|-----------|-----------|------|--------|
| 全部 OCR（当前） | ✅ 但浪费 | ✅ | 慢（10~100x） | ~95% |
| 先文本后 OCR 回退（推荐） | ✅ 完美文本 | ✅ OCR | 自适应 | 文字型 100%，扫描件 ~95% |
| 全部直接提取 | ✅ | ❌ 乱码 | 最快 | 不适用 |

**选择先文本后 OCR 回退的理由**：
- 文字型 PDF（占实际场景 60~80%）直接提取是完美方案——零信息损失、毫秒级
- 扫描件 PDF 回退到 OCR 与当前行为一致，无退化
- 检测逻辑简单可靠：提取后检查长度和 CID 残留比例即可

**质量检测算法**：

```
PdfParser.parse(content, filename):
  text = PyMuPDF.extract_text()  # 直接文本提取

  # 质量评估
  if len(text.strip()) < 50:
    # 提取文本太短，很可能是扫描件 → 回退 OCR
    use_ocr = True
  elif count_cid_residuals(text) / len(text) > 0.05:
    # CID 残留超过 5%，字体映射有问题 → 回退 OCR
    use_ocr = True
  elif has_garbled_unicode(text):
    # 检测到乱码 Unicode → 回退 OCR
    use_ocr = True
  else:
    # 文本质量合格，直接使用
    use_ocr = False

  if use_ocr:
    # 回退到 OCR（与当前 v3.3 流程完全一致）
    pages = PyMuPDF.render_300dpi_png()
    text = Tesseract.ocr(pages, lang='chi_sim+eng')
    text = clean_elements(text)  # OCR 清洗管道
  else:
    # 直接提取的文本也过一遍轻量清洗
    text = normalize_unicode(text)
    text = remove_control_chars(text)
    # 不需要 OCR 专用清洗（fix_common_ocr_errors 等）
```

**性能预期**：
- 文字型 PDF：处理时间从分钟级降至秒级（10~100x 提速）
- 扫描件 PDF：处理时间不变（回退到 OCR）
- 整体处理速度提升取决于上传文档中文字型 PDF 的比例（预估 3~10x 平均提速）

### 3.3 ES 元数据丰富

**新增字段**：

| 索引 | 新增字段 | 类型 | 说明 |
|------|---------|------|------|
| fish-user-knowledge | `doc_name` | keyword | 文档原始文件名（方便检索结果展示来源） |
| fish-user-knowledge | `file_type` | keyword | 文件格式（pdf/docx/xlsx/pptx/html/txt/md） |
| fish-user-knowledge | `token_count` | integer | chunk 的 token 数（质量评估） |
| fish-public-knowledge | `doc_name` | keyword | 同上 |
| fish-public-knowledge | `file_type` | keyword | 同上 |
| fish-public-knowledge | `token_count` | integer | 同上 |
| fish-user-memory | `token_count` | integer | 长期事实的 token 数 |

**ES mapping DDL 变更**（以 fish-user-knowledge 为例）：

```json
{
  "properties": {
    "doc_name":     { "type": "keyword" },
    "file_type":    { "type": "keyword" },
    "token_count":  { "type": "integer" }
  }
}
```

ES 的 dynamic mapping 默认开启，新增字段不需要重建索引——新写入的文档自动使用新 mapping，旧文档这些字段为 null 不影响检索。

**写入侧改动**（`storage/elasticsearch.py`）：

```python
# bulk_index_document_chunks 中每个文档新增字段
doc = {
    "content": chunk_text,
    "embedding": embedding,
    "doc_id": task_id,
    "page_number": element.page_number,
    "chunk_index": idx,
    # v3.5 新增
    "doc_name": filename,       # 从 task 信息传入
    "file_type": content_type,  # 从 task 信息传入
    "token_count": chunk_token_count,
}
```

**检索侧收益**（为后续 v3.6 打基础）：
- `doc_name`：检索结果可展示"来自文档：《xxx》第 3 页"
- `file_type`：可按文件类型做加权（如学术论文权重高于聊天记录导出的 txt）
- `token_count`：质量追踪时能统计 chunk 粒度分布，评估分块策略效果

## 六、验收标准

1. `FISH_WORKER_CHUNK_STRATEGY=flat` 时行为与 v3.4 完全一致（兼容回归）
2. `FISH_WORKER_CHUNK_STRATEGY=structured` 时：
   - Title + Text 合并为一个 chunk（标题不出现在独立 chunk 中）
   - Table 整表 ≤1024 token 时保留完整
   - 普通文本不在句子中间硬切
3. 文字型 PDF 直接文本提取 → 质量合格 → 不走 OCR（速度提升 10x+）
4. 扫描件 PDF 检测到质量差 → 自动回退 OCR（行为与 v3.4 一致）
5. ES 新写入的文档包含 `doc_name`/`file_type`/`token_count` 字段
6. 旧文档缺失新字段时不影响检索（dynamic mapping 兼容）

## 七、已知风险与缓解

| 风险 | 缓解措施 |
|------|---------|
| 句子边界检测对中文标点处理不完整 | 覆盖 `。？！；` + 引号闭合 `」"` + 英文 `.?!;`；特殊排版（无标点的列表项）回退到 token 边界 |
| PDF 质量检测误判（文字型被判为扫描件） | 阈值保守（长度<50 或 CID>5% 才回退 OCR），宁可多 OCR 不肯漏 |
| 结构化分块对无格式 txt 无改善 | txt 只有 Text 类型，自动回退到句子边界对齐的 token 滑窗，与当前行为近似 |
