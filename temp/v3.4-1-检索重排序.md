# v3.4-1 检索重排序（Retrieval Reranking）

> 版本线：v3.4 Phase 1
> 改动范围：仅 Java 后端 `rag/pipeline/` 目录
> 依赖：DashScope Rerank API（与现有 DashScope Embedding 同生态）
> 目标：最小改动获得最大精度提升

---

## 一、解决什么问题

### 问题 1：BM25 与 cosine 分数不可比

当前 `RagRecall.java` 将三路双路（文本 BM25 + 向量 cosine）的检索结果合并时，**直接按 ES 原始 `_score` 排序截断**。

但 BM25 分数通常在 0~15+（取决于文档长度和词频），而 cosine 相似度在 0~1.0 区间。两者不在同一尺度——BM25 的 8 分和 cosine 的 0.85 分无法直接比较。实际效果是**文本路主导了排序**，向量路的高质量语义匹配被压到后面。

**表现**：用户问"如何容器化部署"，向量路能召回包含"Docker Compose 最佳实践"的语义相关文档（cosine 0.87），但文本路一个恰好包含"部署"关键词的低相关文档（BM25 3.2）排在前面，最终 Top-8 截断时语义匹配被丢掉。

### 问题 2：没有精排阶段

当前 RAG 是"初检索 → 截断 → 注入"的**两阶段**流程。初检索用的 bi-encoder（双编码器，即 embedding）虽然快，但精度有限——它只看 query 和 document 各自的 embedding 距离，不交互计算。

业界 RAG 标准做法是**三阶段**：初检索（bi-encoder，求快）→ 重排序（cross-encoder，求精）→ 截断注入。Cross-encoder 将 query 和 document 拼在一起过一遍模型，能捕捉词级别的交互关系，精度显著高于 bi-encoder。

### 问题 3：初检索召回量过小

当前 `per-subquery-size=5`，即每条子查询每路只取 5 条。3 索引 × 2 路 × 5 = 最多 30 条候选，去重后可能只剩 15~20 条。这个候选池对于后续精排来说太小了——如果真正的相关文档在初检索时排名 25，根本进不了候选池。

## 二、方案设计

### 2.1 整体架构变化

```
改动前（v3.3）：
  用户消息 → [可选重写] → [查询扩展] → 三路×双路 ES 并发检索
                                              ↓
                                         按 _score 合并去重
                                              ↓
                                      Top-8 截断 → 注入 SystemMessage

改动后（v3.4）：
  用户消息 → [可选重写] → [查询扩展] → 三路×双路 ES 并发检索
                                              ↓
                                       RRF 分数融合 ← 新增
                                              ↓
                                      候选池 Top-30~50 ← 扩大
                                              ↓
                                    DashScope Rerank API ← 新增
                                              ↓
                                      Top-8 截断 → 注入 SystemMessage
```

### 2.2 新增/修改组件

| 组件 | 类型 | 职责 |
|------|------|------|
| `RagScoreFusion` | 新增 | RRF 分数融合：将 BM25 和 cosine 的 `_score` 统一到同一尺度 |
| `RagReranker` | 新增 | 调用 DashScope Rerank API 对候选结果做 cross-encoder 精排 |
| `RagRecall.java` | 修改 | 在合并去重后插入 RRF → Rerank 两个阶段；扩大 `per-subquery-size` |
| `RagProperties.java` | 修改 | 新增 rerank 和 fusion 相关配置项 |
| `RagRecallConfiguration.java` | 修改 | 注册 `RagReranker` Bean |

## 三、方案详解

### 3.1 RRF 分数融合（RagScoreFusion）

**原理**：Reciprocal Rank Fusion 不看原始分数，只看排名。对每路结果，按排名位置赋分：`score = 1 / (k + rank)`，其中 k=60 是标准参数。多路结果按文档 ID 求和。

**为什么选 RRF 而不是线性加权**：
- 线性加权需要先做 min-max 归一化，但 BM25 分数的分布是**长尾的**（少数高分，多数低分），min-max 会把大多数文档压到 0 附近，区分度差
- RRF 只依赖排名，对分数分布不敏感，鲁棒性更好
- RRF 是 Elasticsearch 8.x 原生支持的融合策略（`rrf` 查询），但我们这里在应用层做更灵活

**实现**：

```
输入：List<SearchHit>（来自三路×双路，共 6 组结果）
处理：
  1. 对每组结果按 _score 降序排列
  2. 每个文档的融合分 = Σ(1 / (60 + rank_in_group))
     - 同一文档在不同组中的排名分别计算后求和
  3. 按融合分降序排列
输出：融合排序后的候选列表（Top-N，N 可配置，默认 50）
```

**配置项**：

| 配置 | 默认值 | 说明 |
|------|--------|------|
| `fish.rag.fusion.enabled` | `true` | RRF 融合开关 |
| `fish.rag.fusion.rrf-k` | `60` | RRF 常数 k（标准值，一般不调） |
| `fish.rag.fusion.candidate-pool-size` | `50` | 融合后候选池大小（喂给 Reranker） |

### 3.2 DashScope Reranker 精排（RagReranker）

**选型对比**：

| 方案 | 精度 | 延迟 | 部署成本 | 中文支持 | 与现有生态契合度 |
|------|------|------|---------|---------|---------------|
| DashScope Rerank API | 高（专门优化中文） | 100~500ms（50条内） | 零（SaaS） | 原生中文优化 | ⭐ 最高（同 API Key、同 SDK） |
| BGE-reranker 本地 | 高 | 50~200ms（需 GPU） | 需 GPU / Ollama | 好 | 中（需额外部署） |
| Cohere Rerank | 高 | 200~400ms | 零（SaaS） | 一般 | 低（海外服务） |
| 不做 Rerank，只做 RRF | 中 | 零 | 零 | — | — |

**选择 DashScope Rerank API 的理由**：
1. 项目已用 DashScope 做 embedding（`text-embedding-v2`），Rerank 共用同一 API Key，零额外配置
2. DashScope Rerank 模型（`gte-rerank`）对中文优化，与项目中文场景完全匹配
3. SaaS 零部署，不增加运维负担
4. 延迟可控：50 条候选 rerank 通常 200~400ms，相比初检索的 100~300ms 是可接受的增量

**API 调用方式**：

```
POST https://dashscope.aliyuncs.com/api/v1/services/aigc/text-rerank/text-rerank
Headers: Authorization: Bearer {DASHSCOPE_API_KEY}
Body: {
  "model": "gte-rerank",
  "input": {
    "query": "用户查询文本",
    "documents": ["候选文档1", "候选文档2", ...]
  },
  "parameters": {
    "top_n": 8,
    "return_documents": false
  }
}

Response: {
  "output": {
    "results": [
      { "index": 3, "relevance_score": 0.95 },
      { "index": 0, "relevance_score": 0.88 },
      ...
    ]
  }
}
```

**实现要点**：

- `RestClient` 在构造时创建一次并复用（非每次调用重建），避免高并发下反复创建 HTTP 工厂
- 接口 `RagReranker` + 内部实现 `DashScopeRagReranker`，降级逻辑完全内聚在实现中，编排层无 if/else
- 响应解析逻辑抽成静态方法 `reorderByResults`，便于脱离 HTTP 单测
- `@ConditionalOnProperty(prefix = "fish.rag", name = "enabled", havingValue = "true")` 守卫 Bean 注册

```
输入：融合后的候选池（最多 50 条）+ 原始用户查询
处理：
  1. 提取候选文档的 content 字段，构建 documents 列表
  2. 调用 DashScope Rerank API，传入 query + documents
  3. 按 API 返回的 relevance_score 降序排列
  4. 截取 Top-8（max-injected-facts）
输出：精排后的最终注入列表
```

**降级策略**（三级）：
- `rerank.enabled=false` 或 `apiKey` 为空 → 跳过 Rerank，直接用 RRF 融合结果截断
- Rerank API 调用失败（超时/限流/网络错误）→ `fallback-on-error=true` 时记 WARN 日志并回退；`false` 时向上抛异常
- Rerank 返回结果为空 → 回退到 RRF 融合结果

**配置项**：

| 配置 | 默认值 | 说明 |
|------|--------|------|
| `fish.rag.rerank.enabled` | `true` | Rerank 开关 |
| `fish.rag.rerank.model` | `gte-rerank` | DashScope Rerank 模型名 |
| `fish.rag.rerank.top-n` | `8` | 精排后保留条数（= max-injected-facts） |
| `fish.rag.rerank.timeout-seconds` | `5` | API 调用超时 |
| `fish.rag.rerank.fallback-on-error` | `true` | 失败时回退到 RRF 结果 |

### 3.3 初检索召回量扩大

当前 `per-subquery-size=5`，需要扩大以为 Reranker 提供足够候选。

**调整方案**：

| 配置 | 改动前 | 改动后 | 说明 |
|------|--------|--------|------|
| `per-subquery-size` | 5 | **10** | 每条子查询每路取 10 条 |
| `knn-num-candidates` | 80 | **120** | HNSW 候选集扩大，保证向量路召回量 |

扩大后理论最大候选：10 条/路 × 6 路 = 60 条（去重后通常 30~50 条），喂给 Reranker 精排。

**ES 负载评估**：
- per-subquery-size 从 5→10：单次检索返回数据量翻倍，但 ES 的分页查询成本主要在评分阶段，10 条的额外开销可忽略
- knn-num-candidates 从 80→120：HNSW 图遍历多走 40 个节点，P95 延迟增加约 5~10ms，可接受

### 3.4 完整数据流

```
用户消息："Docker Compose 怎么配置"

  ↓ [可选] RagQueryRewrite（当前默认关闭）

  ↓ RagQueryExpand → 子查询列表
     ["Docker Compose 配置", "Docker Compose 基本使用", ...]

  ↓ 三路×双路 ES 并发检索（per-subquery-size=10）
     UserMemorySearcher   (text: 10 + vector: 10)
     UserKnowledgeSearcher(text: 10 + vector: 10)
     PublicKnowledgeSearcher(text: 10 + vector: 10)
     → 每条子查询最多 60 条，N 条子查询共 60N 条

  ↓ RagScoreFusion（RRF 融合）
     按 RRF 分数排序 → 候选池 Top-50

  ↓ RagReranker（DashScope Rerank API）
     50 条 → gte-rerank 精排 → Top-8

  ↓ renderBlock → 注入 SystemMessage
```

## 六、验收标准

1. `fish.rag.rerank.enabled=false` 时行为与 v3.3 完全一致（回归测试）
2. `fish.rag.rerank.enabled=true` 时 Reranker 调用成功，返回结果按 relevance_score 排序
3. Rerank API 超时/失败且 `fallback-on-error=true` 时自动降级，不抛异常到上层对话流
4. Rerank API 失败且 `fallback-on-error=false` 时异常向上传播（不静默吞掉）
5. RRF 融合后文本路和向量路的高质量结果都能进入候选池
6. 新增配置项都有合理默认值，零配置即可使用（复用 `DASHSCOPE_API_KEY`）
7. `RestClient` 构造一次复用，非每次调用重建
