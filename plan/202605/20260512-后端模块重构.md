## 执行原则（策略 A：原子操作）

每个**模块内**按以下顺序完整执行后，才运行编译验证：

1. 在目标路径创建所有新文件，修改 `package` 声明
2. 立即全局搜索并替换所有文件中的旧 `import` → 新 `import`（必须在删除前完成，否则中间状态无法编译）
3. 删除全部旧文件
4. 运行 `mvn compile -q` 验证本模块无编译错误，再进入下一阶段

> 不能在 import 未更新完之前就删除旧文件，否则所有依赖该包的文件会立即报红。

### 审查发现

#### memory ↔ rag 双向依赖（设计问题，非 bug）

计划中标注的依赖方向为 `rag → memory`（单向），实际执行后发现存在反向引用：

```
memory.longterm.ElasticsearchLongTermMemoryStore
  → import rag.document.UserMemoryDocument

rag.service.KnowledgeManageService
  → import memory.config.MemoryProperties

rag.service.OrphanTaskCompensationService
  → import memory.config.MemoryProperties

rag.pipeline.recall.UserMemoryElasticsearchSearcher
  → import memory.config.MemoryProperties
```

**原因**：重构前 `UserMemoryDocument` 和 `ElasticsearchLongTermMemoryStore` 在同一个包 `agent/memory/longterm/` 下，拆分后自然分到了不同模块。

**影响**：编译和运行均无问题（同 JVM、无循环 bean 注入）。仅在未来拆分为独立 jar 时才会有实际影响。

**可选修复**：将 `UserMemoryDocument` 移至 `memory/longterm/`（它本质上是 memory 的 ES 文档模型），使依赖恢复为 `rag → memory` 单向。当前不修复也不影响功能。
