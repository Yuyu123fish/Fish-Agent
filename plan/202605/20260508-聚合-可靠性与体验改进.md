## 一、SSE persist 异常阻断 emitter.complete()

### 问题

`ChatService.onComplete` 回调中，`persist()` 与 `emitter.complete()` 在同一个 try 块内。若 `persist()` 抛异常（RustFS 宕机、磁盘满），`safeSend("done")` 和 `emitter.complete()` 都被跳过 → 前端永远收不到 done → SSE 连接挂住直到 5 分钟超时 → 会话锁和 SSE 并发槽被无意义占用。

### 方案选型

| 方案 | 做法 | 为什么选/不选 |
|------|------|-------------|
| **A. persist 独立 try-catch** | `persist()` 单独包裹 catch，失败仍发 done + complete | **选定。** fail-safe 思路——emitter 生命周期不应被持久化阻塞。与同级的 `triggerMemoryCompressionIfNeeded`（异步+catch）保持一致 |
| B. persist 失败带错误标记 | done 事件加 status 字段区分成功/失败 | 需改前端 done 事件处理，改动面大，且 persist 失败对用户无感知价值 |
| C. persist 改异步 | 移到 CompletableFuture | 异步线程中 UserContext 已清理，需额外传参；且 persist 结果应同步可知 |

### 落地

`ChatService.java` onComplete lambda 中 `persist()` 被独立 try-catch 包裹，异常时 `log.error` 但不阻塞后续 `safeSend("done")` + `emitter.complete()` + 异步触发。

## 二、会话重命名端点（PATCH + CORS 放行）

### 问题

会话标题由后端首条消息时自动生成（截断用户输入前 200 字），之后无法修改。

### 端点设计选型

| 方案 | 做法 | 为什么选/不选 |
|------|------|-------------|
| **A. PATCH /sessions/{sid}** | 标准 RESTful 局部更新 | **选定。** PATCH 语义精确（部分更新 title），未来可扩展其他字段 |
| B. PUT /sessions/{sid} | 全量替换 | 语义为全量替换，但当前只需改 title，过重 |
| C. POST /sessions/{sid}/rename | 自定义动作端点 | 不符合 RESTful 约定，且路由冗余 |

### 后端实现要点

**`ChatMetadataService.renameTitle()`**：
- `selectOne` 条件包含 `sessionId + userId`，**校验所有权**（非当前用户的会话不可改）
- 复用 `trimTitle()` 截断清洗（换行替换、200 字上限）
- 同步 touch `updatedAt`，保证侧栏排序正确

**`ChatController`**：
- `@RequestBody Map<String, String>` 接受 `{ "title": "..." }`
- `title == null || isBlank()` 时抛 `IllegalArgumentException` → 全局 400

### 踩坑：CORS 缺少 PATCH

**问题**：前端发 PATCH 请求返回 403。

**根因**：`WebMvcConfig.addCorsMappings()` 的 `allowedMethods` 只有 `GET, POST, PUT, DELETE, OPTIONS`，缺少 `PATCH`。浏览器 preflight OPTIONS 请求被拒。

**修复**：`allowedMethods` 补充 `"PATCH"`。

**教训**：新增 HTTP 方法端点时，必须同步检查 CORS 白名单。

## 三、HTTP 错误契约与前端消费策略

### 问题

后端 `GlobalExceptionHandler` 统一返回 JSON 格式错误：

```json
{ "code": "SESSION_LOCKED", "message": "此会话正在处理中..." }
```

但前端 `streamChat` 的非 200 处理直接 `handlers.onError?.('HTTP ${status}：${text}')` —— 原始 JSON 裸露给用户。

### 方案选型

| 方案 | 做法 | 为什么选/不选 |
|------|------|-------------|
| **A. 前端解析 409 JSON** | `streamChat` 对 409 特殊处理，解析 JSON 提取 message | **选定。** 不破坏后端统一 JSON 格式；后端 message 已是中文，前端只需正确提取 |
| B. 后端 409 返回纯文本 | 改 `GlobalExceptionHandler` 返回纯文本 | 破坏后端统一 JSON 错误格式，所有端点的错误格式应一致 |
| C. 前端通用 HTTP 错误解析器 | 所有非 2xx 都解析 JSON 并提取 message | 过度设计，当前只有 409 需要特殊处理 |

### 设计原则

后端错误格式应保持**统一 JSON 结构**（`{ code, message }`），前端按 status code + `code` 字段做精细化处理。这保证了：
- 后端 `GlobalExceptionHandler` 是唯一错误格式定义点
- 前端只需对特定 status code 做分支，不需要为每种错误写不同解析逻辑
- 未来新增错误类型（如 429 限流）只需前端加一个 status 分支

### 落地

`api/chat.ts` 的 `!resp.ok` 分支：409 → 解析 JSON → `SESSION_LOCKED` 时展示中文 message；其他错误统一显示 `请求失败 (status)`。

## 四、SSE tool 事件数据格式

### 现状

后端通过 `emitter.send(SseEmitter.event().name("tool").data(...))` 推送工具调用信息。前端 `api/chat.ts` 解析 `event: tool` 的 data 字段，尝试 JSON parse 提取 `name` + `payload`，解析失败则 data 整体作为工具名。

### 前端消费策略

`MessageBubble.vue` 新增 `friendlyToolName` computed，将后端工具名（`knowledge_search`、`web_search` 等）映射为中文。**映射表在前端维护**，不需要后端改动。

**为什么在前端映射而非后端**：
1. 工具名是技术标识符，后端不应关心展示层的中文名
2. 前端可随时新增映射，无需后端发版
3. 未映射的工具名直接展示原名，降级优雅

## 五、前端资源生命周期保障

三项前端可靠性改进，涉及后端契约的部分较少，简要记录：

### 5.1 AbortController 卸载清理

`chat.ts` 新增 `cleanup()` 函数 + `ChatView.vue` 的 `onUnmounted` 调用。组件卸载时 abort 残留 fetch，避免内存泄漏。与后端 SSE 5 分钟超时形成**双保险**：前端主动断开 + 后端超时兜底。

### 5.2 全局错误边界

`App.vue` 的 `onErrorCaptured` + `main.ts` 的 `app.config.errorHandler` 双层兜底。捕获组件异常后展示降级页面（带"重试"按钮），而非白屏。

### 5.3 长对话渐进式渲染

`MessageList.vue` 仅渲染最近 30 条消息，顶部"加载更多"按钮追加。`:key` 使用全局索引保证 loadMore 时已有 DOM 不重渲染。**不影响后端**——数据仍是全量加载，只是前端裁剪渲染窗口。

## 核心设计原则总结

1. **fail-safe**：emitter 生命周期不应被持久化失败阻塞
2. **统一错误格式**：后端所有错误走 JSON，前端按需精细化消费
3. **RESTful 语义**：新增端点用 PATCH 不用 POST/PUT
4. **前后端职责分离**：工具名映射在前端，后端只发技术标识符
5. **CORS 同步**：新增 HTTP 方法端点时必须检查 CORS 白名单
