## 一句话定位 & 本模块亮点

基于 **SseEmitter** 的 POST SSE 流式对话，前端 Fetch + ReadableStream 逐字渲染；**令牌桶 + SSE 并发槽 + 会话互斥锁** 三层防护，429/409 区分频率与并发拒绝。

- **SSE 而非 WebSocket**：对话是请求-响应单向推送，复用 HTTP 拦截器链用 401/429/409 拒绝，无需协议升级。
- **三层防护分工**：令牌桶管频率（惰性 refill，1 token/s）、SSE 槽管并发（同用户 2 路）、会话锁管竞态（同 session 1 路）——互补不重叠，全在 Redis（跨实例）。
- **回调注册顺序防锁泄漏**：先注册 emitter 回调再 subscribe，否则 Reactor onComplete 异步先触发 emitter.complete 导致 onCompletion 丢失、会话锁永久泄漏。
- **合并释放**：SSE DECR + 会话锁 DEL + dispose 全塞进 `releaseSseSlotOnce`，AtomicBoolean 保幂等。
- **Token 预算**：按模型窗口算 inputBudget，P0 输入 + P1 系统先留，剩余 window 40%/RAG 25%/summary 20%/excerpt 10%/state ~5%，emergencyTrim 二次兜底。**[v6.3] 窗口来自 `ActiveChatModelContext` 单真相源（与工具结果治理共用，迁移不再漏改 override）。**
- **CAS 生命周期**：ChatTurnLifecycle 一次性 finish 回调覆盖五路终止，落 trace + 清 scratch，AtomicBoolean 保证只跑一次。
- **MDC traceId 全链路**：TraceFilter 入口注入 → MdcAsync 异步传播 → Reactor/SSE 回调手动恢复 snapshot。

## 一、SSE 流式对话：为什么不用 WebSocket/EventSource

### 背景

LLM 流式输出要"服务端持续推 token"。WebSocket 全双工、EventSource 浏览器原生，但都有问题。

### 问题与方案

选 **SSE（SseEmitter）+ POST + Fetch/ReadableStream**：

- 对话是**请求-响应单向推送**（用户 POST 一条 → 服务端流式回一条），WebSocket 的双向能力浪费；
- SSE 是纯 HTTP，**复用整个拦截器链**（鉴权→限流→会话锁）用标准 401/429/409 拒绝，WebSocket 得自定义错误协议；
- 无需协议升级，Nginx/CDN 开箱即用。
- 为什么不用浏览器原生 `EventSource`：它只支持 GET，聊天要 POST 发 body，所以用 `Fetch + ReadableStream` 手动解析 SSE 流（附带 AbortController 可靠中止）。

### 追问

**1. 为什么不用 WebSocket？**
本项目对话是单向推送，WebSocket 双向能力无用武之地；且 SSE 能直接复用 HTTP 拦截器链用状态码拒绝，不用在 WS 帧里自定义错误协议，代理兼容也更好。

**2. POST SSE 为什么不用 EventSource？**
EventSource 只支持 GET 不能带 body，聊天要 POST 发用户消息 JSON，所以用 Fetch + ReadableStream 手写 SSE 解析（约 30 行）。

## 二、三层防护：令牌桶 + SSE 并发槽 + 会话互斥锁

### 背景

聊天要防三类滥用：频率（刷屏）、并发（同用户开多路流占资源）、竞态（同 session 两条消息打架）。

### 问题与方案

```
POST /api/chat/stream
  ↓ TraceFilter: MDC.put(traceId)
  ↓ 令牌桶检查 → 不够？429 RATE_LIMIT_EXCEEDED
  ↓ SSE INCR 并发槽 → 超限？Lua 内 DECR 回滚 → 429 CONCURRENT_LIMIT_EXCEEDED
  ↓ SET NX 会话锁 → 已被占？先归还 SSE 槽再 409 SESSION_LOCKED
  ↓ 正常流式
```

- **令牌桶（管频率）**：Redis Lua **惰性 refill**——无后台线程，每次请求算 `(now - lastRefill) × rate` 补充令牌再扣 1。默认 60 桶容量 + 1 token/s，支持突发（用户沉默时积累、爆发时用完）。
- **SSE 并发槽（管并发）**：仅 POST /stream，Redis Lua `INCR` + 超限 `DECR` 回滚，默认同用户 2 路。**先 INCR 再判断、超限才回滚**，整个判断在 Lua 原子体内，避免 GET-then-SET 竞态。
- **会话互斥锁（管竞态）**：`SET NX EX 120`，同 session 1 路，正常路径主动 DEL，120s TTL 兜底。

**429 vs 409**：频率/并发超限用 429（带 retryAfter 指导重试，不触发 Nginx upstream retry）；同 session 冲突用 409（sessionId 是资源的一部分，冲突语义最贴）。

### 追问

**1. 令牌桶 refill 为什么不用定时任务？**
定时任务要后台线程、精度依赖调度间隔。惰性计算零额外线程、精度到毫秒、Redis Lua 一次完成 refill+consume。代价是 key 有 TTL，长期不发请求的用户 key 过期，下次满桶开始——正是期望行为。

**2. 为什么用令牌桶不用漏桶/固定窗口？**
聊天天然突发（连发几条再等回复）。漏桶强制排队会让第 2-3 条消息排队、TTFB 恶化；固定窗口有边界突刺（59:59 发 60 次 + 00:01 又 60 次 = 2 秒 120 次）。令牌桶允许桶容量内突发、突发后平滑限制，最自然。

**3. Redis 挂了限流怎么办？**
fail-open：Lua 抛异常 catch 后放行。限流是保护机制不应成单点故障，Redis 恢复后自动恢复限流。

**4. 多实例部署限流还正常吗？**
完全正常——这是选 Redis 不选 JVM 内存的核心原因。令牌桶/并发槽/会话锁全在 Redis，两实例共享同一 key，Lua 原子无竞态。

## 三、回调注册顺序防锁泄漏 + 合并释放（本模块最难）

### 背景

系统用 SSE 并发限流 + 会话互斥锁控制并发：拦截器先对 SSE 槽 INCR，抢到会话锁后才订阅 ReactAgent 流，流结束才释放槽位和锁。

### 问题与方案

测试中发现**某些会话锁永远不释放**（后续全 409）。根因：**emitter 回调注册和 Reactor subscribe 的时序竞争**——若先 subscribe 再注册 onCompletion，Reactor 的 onComplete 可能在回调注册前异步触发 emitter.complete() → onCompletion 丢失 → `releaseSseSlotOnce` 永不执行 → 锁泄漏。

修复：**①先创建 `releaseSseSlotOnce` → ②注册 emitter 回调 → ③最后 subscribe**。`Disposable` 用数组引用桥接（subscribe 后才产生实例）。

**合并释放**：`SseEmitter` 每个生命周期事件只能注册一个回调（后注册覆盖前者），所以 SSE DECR + 会话锁 DEL + dispose 全塞进同一个 `releaseSseSlotOnce`，`AtomicBoolean` 保幂等（onTimeout/onCompletion/onError 都触发也只跑一次）。

### 追问

**1. 为什么回调必须在 subscribe 之前注册？**
Reactor onComplete 是异步的，先 subscribe 可能在 onCompletion 注册前就触发 emitter.complete()，回调永久丢失、锁泄漏。这是实际踩的坑，排查靠在回调加日志发现某些会话的 onCompletion 从没出现过。

**2. 多个地方都要在 onCompletion 加逻辑怎么办？**
合并模式：所有释放逻辑塞进同一个 Runnable 注册到 onCompletion，后续新增只在 Runnable 内部追加，不改外层。

## 四、Token 预算 + CAS 生命周期

### 背景

拼 prompt 时历史/RAG/摘要/摘录都可能很长，不控总量会超模型窗口被截断或报错。另外一轮对话有多种终止方式（正常/异常/超时/客户端断），收尾（落 trace、清 scratch）要保证只跑一次。

### 问题与方案

**Token 预算**（`ContextBudgetAllocator`）：按当前模型窗口算 `inputBudget = max(1000, window×(1-safety) − outputReserve)`，P0 当前输入 + P1 系统指令先预留，剩余按权重 window 40% / RAG 25% / summary 20% / excerpt 10% / state ~5% 切。每段注入前 `TokenEstimator.estimate` 检查自身预算、超了截断标 trimmed；**二次兜底 emergencyTrim**：总量仍超时只留 P1 系统 + P0 输入 + 尽量多近期窗口，丢所有增强上下文保证本轮能跑。模型窗口经 `ActiveChatModelContext` 单真相源取（命中 `model-context-overrides` 否则回退默认，[v6.3] 与工具结果治理共用）。

**CAS 生命周期**（`ChatTurnLifecycle`）：每轮 `start(chatMetrics, callback)` 包裹，callback 用 AtomicBoolean CAS 保证整轮只执行一次，**五路终止都触发**——正常 success / 流式 error / SSE timeout / SSE completed-before-finish / 抢锁或组装失败。callback 内：`finishTurn` 收尾 trace → `persistAsync` 写 ES → `clearScratch(turnId)` 清工具结果 scratch 两 key。

### 追问

**1. Token 预算怎么定的？为什么按权重切不按需切？**
按权重（window/RAG/摘要/摘录/状态固定比例）切保证行为可预测、好调参；P0 输入和 P1 系统先留保证核心信息不丢。emergencyTrim 是二次兜底，正常路径各段按自身预算截断即可。**[v6.3] 模型窗口从 `ActiveChatModelContext` 取（单真相源），与工具结果治理共用——V3→V4 迁移漏改 override 就是因为窗口散落两处各取，收口后只改一处。**

**2. emergencyTrim 什么时候触发？**
各段都按预算截断后，若总量（含段间分隔符开销）仍超 inputBudget 才触发——只留系统必需 + 当前输入 + 尽量多近期窗口，丢摘要/RAG/摘录/状态。是"宁可丢增强也要本轮能跑"的最后防线。

**3. 一轮对话有多个终止信号（既 timeout 又 error）怎么办？**
ChatTurnLifecycle 的 finish callback 用 AtomicBoolean CAS，整轮只执行一次——哪怕 timeout 和 error 并发到达，落 trace + 清 scratch 也只跑一次。

## 最难/最有挑战：SSE 回调注册顺序导致的会话锁泄漏

### 问题

测试中发现某些会话锁永不释放（后续该 session 全 409）。

### 挑战

根因是 emitter 回调注册和 Reactor subscribe 的时序竞争——Reactor onComplete 异步，先 subscribe 可能在 onCompletion 注册前就触发 emitter.complete()，回调丢失。

### 解决方案

严格 ①创建 `releaseSseSlotOnce`（AtomicBoolean 幂等）→ ②注册 emitter 回调 → ③最后 subscribe；`Disposable` 用数组引用桥接。

### 面试回答要点

> "这是实际遇到的 bug。Reactor 的 onComplete 异步——先 subscribe 再注册 onCompletion，可能在回调注册前就触发 emitter.complete()，onCompletion 永不执行、会话锁泄漏。修复很简单：先注册回调再 subscribe。但发现根因很难——日志显示锁没释放，却不知道为什么回调没触发，靠在回调加日志才发现某些会话的 onCompletion 从没出现过。"
