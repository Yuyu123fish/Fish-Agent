# 模块 6：认证与多租户（面试复盘版）

> - **配套详细版**：`../模块6-认证与多租户.md`
> - **本版定位**：现场复盘口述体，保留少量关键代码。
> - **内容范围**：自定义 token + Redis Session + BCrypt + ThreadLocal 显式快照 + ES user_id 隔离（均对齐当前代码）。

---

## 一句话定位 & 本模块亮点

自定义 token + Redis Session 无状态鉴权，`GlobalAuthInterceptor` + `ThreadLocal<UserContext>` 全链路携带用户身份，ES 三索引以 `user_id` term filter 强制隔离私有数据，虚拟线程下显式快照回放防 ThreadLocal 丢失。

- **自定义 token + Redis Session（不用 JWT/Spring Security）**：UUID 32 字符 token，Redis `fish:session:{token}` 存 UserContext，`GET`+`EXPIRE` 续期，`DEL` 即登出/封禁即时生效。
- **BCrypt 密码哈希**：cost=10（~1024 轮，几百 ms），内建 salt，抗 GPU；只引 `spring-security-crypto` 不引完整 Spring Security。
- **HandlerInterceptor 鉴权**（非 Filter 非 AOP）：能拿 Spring Bean、`return false` 终止、异常进 `@ExceptionHandler`。
- **ES 三索引隔离**：私有记忆/知识 `user_id` filter、公共知识无 filter；`source_type=chat` 防御性约束。
- **虚拟线程 ThreadLocal 显式快照-回放-清理**（最难）：解决 JDK 21 虚拟线程 carrier thread 切换导致 ThreadLocal 隐形丢失。

## 一、自定义 token + Redis Session（不用 JWT/Spring Security）

### 背景
项目鉴权需求极简：登录→发 token→每次请求带 token→验 Redis 有没有→放行。

### 问题与方案
- **Token**：`UUID.randomUUID().replace("-","")`（32 字符），`SETEX fish:session:{token} 86400 {UserContext JSON}`，每请求 `GET` + `EXPIRE` 续期（24h 内有操作永不过期）。
- **登出/封禁即时生效**：`DEL fish:session:{token}`——这是相比 JWT 的核心优势（JWT 不可撤回，得配黑名单退化成 Redis Session，不如直接用 Redis）。
- **不用 Spring Security**：只需 BCrypt + token 登录 + Redis Session + 白名单，引入它要关十几种默认行为、配 FilterChain，约 300 行自写代码完全可控。

```java
// GlobalAuthInterceptor.preHandle
if (isWhiteListed(uri)) return true;
String token = request.getHeader("X-Auth-Token");
if (token == null || token.isBlank()) { response.sendError(401); return false; }
UserContext ctx = redisSessionManager.findByToken(token);
if (ctx == null) { response.sendError(401, "会话已过期"); return false; }
redisSessionManager.renewToken(token);   // TTL 续期
UserContextHolder.set(ctx);              // 写 ThreadLocal
return true;
```

### 追问

**1. 为什么不用 JWT？**
JWT 签发后不可撤回，登出/封禁/角色变更要"立即生效"就得配黑名单，退化成 Redis Session。与其绕一圈不如直接 Redis：有 key 就是登录、DEL 就是登出，排障审计谁都看得懂。代价是每请求多一次 Redis GET+EXPIRE（微秒级）。

**2. 为什么不用 Spring Security？**
只需 BCrypt + token + Redis Session + 白名单，引入完整 Spring Security 要关 CSRF/Session 固定保护/FilterChain 等十几种默认行为。当前 1 Interceptor + 1 SessionManager + 1 AuthService + BCrypt 约 300 行可控。要接 OAuth2 再引入不迟。

**3. 401 和 403 怎么区分？**
401 未认证（无 token 或 session 不存在，GlobalAuthInterceptor 拦）；403 已认证但无权限（角色不足，PermissionInterceptor/Controller 内 role 判断）。

## 二、BCrypt 密码哈希

### 背景
密码不能明文存，要抗暴力破解和彩虹表。

### 问题与方案
**BCrypt**（cost=10，~1024 轮，单次几百 ms）：
- 内建 salt（自动生成嵌入输出 `$2a$10$...`），`matches(raw, encoded)` 一行比较；
- 天然抗 GPU（Blowfish 密钥扩展的内存访问模式难以并行加速）；
- Spring Security Crypto 直接提供，不引完整 Spring Security。

不选 SHA-256（GPU 每秒数十亿、彩虹表反查）、不选 Argon2（更安全但 Spring 内建支持不如 BCrypt 成熟、需引 Bouncy Castle）。

### 追问

**1. 为什么 BCrypt 比 SHA-256 安全？**
SHA-256 纳秒级、GPU 可暴力、相同密码哈希相同彩虹表反查。BCrypt 慢（几百 ms）+ 内建 salt + Blowfish 结构抗 GPU，暴力破解成本不可逾越。慢正是密码哈希的安全特性。

## 三、多租户隔离：ES user_id filter

### 背景
私有记忆/知识只能本人可见，公共知识所有人共享。

### 问题与方案
ES 三索引物理隔离 + 服务端拼 `user_id` term filter（**不由前端传入，从 UserContextHolder 取**，用户无法篡改）：

| 索引 | filter | 可见性 |
|------|--------|--------|
| `fish-user-memory` | `user_id` + `source_type=chat` + `must_not superseded` | 仅本人 active 事实 |
| `fish-user-knowledge` | `user_id` | 仅本人文档切片 |
| `fish-public-knowledge` | 无 | 全员共享 |

`source_type=chat` 是防御性约束（防历史 bug 把文档切片误写入记忆索引）；另外加 `must_not superseded=true` 让被取代的失效事实（北京→上海的旧"北京"）不召回。

### 追问

**1. 为什么 filter 加 user_id 还要加 source_type=chat？**
防御性：历史 bug 或迁移可能把 document 切片误写入 memory 索引，`source_type=chat` 确保即使误写入也不会被当"用户记忆"召回。代价为零（term filter 走倒排索引）。

**2. 多租户隔离多实例有漏洞吗？**
没有。user_id 来自 Redis Session（每请求从 Redis 重取，不缓存 JVM），filter 服务端拼接、用户无法篡改（不从前端取）。所有实例共享同一 Redis session 存储，换实例绕不过鉴权。

## 四、虚拟线程 ThreadLocal 显式快照（本模块最难）

### 背景
JDK 21 虚拟线程 + `ThreadLocal<UserContext>` 传递用户身份。Servlet 线程写入，Service/DAO 读取。

### 问题与方案
RAG 检索/记忆压缩用 `CompletableFuture.runAsync()` 异步执行——虚拟线程 ForkJoinPool 的 carrier thread 可能切换，**ThreadLocal 不自动传递**。现象：RAG 日志 `user_id` 始终 null、私有知识检索返回空。

**显式快照-回放-清理三步**：
```java
final UserContext snapshot = UserContextHolder.get();          // 入口快照
CompletableFuture.runAsync(() -> {
    if (snapshot != null) UserContextHolder.set(snapshot);     // 异步回放
    try { /* 需要 userId 的逻辑 */ }
    finally { UserContextHolder.clear(); }                     // 防泄漏
});
```

不选 `InheritableThreadLocal`（线程池复用有脏值风险）、不选 `ScopedValue`（Spring Boot 3.5 未适配）。项目把同模式封装成 `MdcAsync` 给 MDC traceId 用——11 处异步任务全迁移。

### 追问

**1. 这个 bug 怎么发现的？**
RAG 检索日志 user_id 始终 null、私有知识返回空。排查发现 RagRecall 用 runAsync 跑并发检索，虚拟线程 carrier 切换时 ThreadLocal 丢失。最坑的是**不是必现**——取决于 ForkJoinPool 调度，调试碰巧没切换就过了，上线随机触发。

**2. 为什么不用 InheritableThreadLocal？**
线程池场景子线程是复用的，第二次提交可能带第一次的脏值。ScopedValue（Java 21 preview）Spring 还没适配。显式传递三步可控、虚拟线程和线程池通吃。

---

## 最难/最有挑战：虚拟线程下 ThreadLocal 的"隐形丢失"

### 问题
虚拟线程 carrier thread 切换时 ThreadLocal 不保证传递。

### 挑战
不是 100% 复现——取决于 ForkJoinPool 调度，调试时碰巧没切换就通过，上线随机触发，RAG 私有检索返空。

### 解决方案
显式快照-回放-清理三步（入口存局部变量、异步 lambda set 回去、finally clear），封装 `MdcAsync` 给 MDC 用。

### 面试回答要点
> "虚拟线程下 ThreadLocal 丢失是 JDK 21 已知行为——carrier 切换不保证传递。最坑的是不必现，取决于调度。解法是显式快照-回放-清理三步，代码只多三行但完全可控。InheritableThreadLocal 线程池有脏值，ScopedValue Spring 没适配，显式传递当前最稳。"
