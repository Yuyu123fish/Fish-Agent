# Fish-Agent v5.6 OTel 链路层下线

> 日期：2026-06-13
> 主题：移除 OpenTelemetry / OTLP / 分布式链路追踪，保留 Prometheus 指标与日志 MDC traceId
> 来源方案：`temp/OTel链路层下线方案-20260613.md`（已实施）
> 与 v5.5 关系：v5.5 引入了「Actuator + Micrometer + OTel + OTLP + Collector」完整可观测管道；v5.6 把其中依赖 Collector 容器的 OTel 链路部分整体下线，零基础设施成本的指标与日志 traceId 全部保留。

## 一、背景与动机

v5.5 一并引入了分布式链路追踪：`micrometer-tracing-bridge-otel` + `opentelemetry-exporter-otlp` + `otel-collector` 容器（→ ES → Kibana）。
实际运行中 Collector 容器未常驻，应用每批次导出 span 都报：

```text
Connection refused localhost:4318   （ERROR 日志噪音）
```

三向核实（无容器 / 无 4318 端口监听 / 守护进程未起）后判定：当前是单体部署，分布式链路追踪的收益不足以抵消额外维护一个 Collector 容器的成本。

决策（「不搞云原生」）：**整体下线 OTel 链路层**，但**保留**对排查仍有价值、且零基础设施成本的两块能力：

- **Micrometer Prometheus 指标**——一个被动 HTTP 抓取端点，无需容器；
- **日志 MDC traceId**——`TraceFilter` / `MdcAsync`，非 OTel，v5.0 起就有。

## 二、下线范围与判定原则

**判定原则**：是否属于 OTel / 是否依赖 Collector 容器。

| 类别 | 判定 | 处置 |
|---|---|---|
| OTel bridge / OTLP 导出 / Collector 容器 / 手埋 span / traceId 关联 | 真·OTel，依赖容器 | **删除** |
| Actuator + `micrometer-registry-prometheus` + ChatMetrics 计时 + `@Observed` + 分位数 | 纯 Micrometer，无容器 | **保留** |
| `TraceFilter` / `MdcAsync` / `TraceConstants`（日志 MDC traceId） | 非 OTel，v5.0 起就有 | **保留** |

> `@Observed` 经 OTel bridge 时会额外产出 span；移除 bridge 后退化为纯 Micrometer 观测定时器，仍记录 `rag.recall` 耗时，功能不丢。

public final class ChatTurnLifecycle {
    private final ChatMetrics chatMetrics;
    private final Timer.Sample sample;
    private final AtomicBoolean finished = new AtomicBoolean(false);

    public static ChatTurnLifecycle start(ChatMetrics chatMetrics) {
        return new ChatTurnLifecycle(chatMetrics, chatMetrics.startSample());

    }
}

## 四、保留的能力（明确边界）

下线 OTel **不等于**下线可观测性。以下能力全部保留并仍由测试覆盖：

| 能力 | 载体 | 说明 |
|---|---|---|
| 业务指标 | `ChatMetrics` + Prometheus 端点 | `fish.chat.turn.duration{outcome=success|error}`、`fish.rag.recall.duration{leg=...}` |
| RAG 观测入口 | `@Observed("rag.recall")` | 退化为纯 Micrometer 定时器，仍记录 `rag.recall` 耗时 |
| Spring AI 原生指标 | Spring AI Observation | `gen_ai.*` 系列指标不依赖 OTel bridge |
| 缓存 / 熔断指标 | Actuator 自动绑定 | `cache_gets`、`resilience4j_circuitbreaker_*` |
| 日志 traceId | `TraceFilter` + `MdcAsync` | 请求级 traceId 注入，Reactor/SSE 异步回调手动恢复 |
| SSE 收尾幂等 | `ChatTurnLifecycle` CAS | timeout / 断连 / cancel / Reactor error+complete 只记一次 |

## 六、面试 Trade-off

| 问题 | 回答要点 |
|------|----------|
| 为什么连 span 一起删，不只删 Collector？ | OTel bridge / OTLP 导出 / 手埋 span 离开 Collector 就只剩噪音；单体部署下日志 traceId + 业务指标已够用，留下半套只会增加心智负担。 |
| 为什么保留 Prometheus？ | 它是被动 HTTP 抓取端点，零额外基础设施，仍覆盖 JVM / HTTP / 业务 / 缓存 / 熔断指标，是「成本≈0、收益明确」的那一半。 |
| 移除 bridge 后 `@Observed` 还有效吗？ | 有效。它退化为纯 Micrometer 观测定时器，不再产出 span，但 `rag.recall` 耗时照常记录。 |
| `RagTraceDocument.traceId` 怎么办？ | 回退随机 UUID，继续作为 RAG 质量文档自身的追踪字段；代价是无法再与请求日志按 traceId 关联（已无 span 层，可接受）。 |
| 怎么保证删除不破坏编译？ | `@RequiredArgsConstructor` 删字段即自动缩构造器；逐一核对删除类与删除 API 的引用点（0 残留）；`DefaultAugmentation` 形参与唯一调用点对齐。 |
