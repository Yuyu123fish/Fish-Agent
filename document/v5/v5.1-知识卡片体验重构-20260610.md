# Fish-Agent v5.1 知识卡片体验重构

> **版本**：v5.1
> **日期**：2026-06-10
> **范围**：SM-2 间隔重复复习系统 · 三栏布局 · 可展开卡片 · 两层工具栏 · 复习统计 · 响应式打磨
> **前置版本**：v5.0（后端工程化提升）
> **后端 Java 源文件约 158 个**（+10 新增）

---

## 一、更新目标

v4.1–v4.2 构建了知识卡片的基础能力（AI 提取、CRUD、关键词、图谱、分组、关联），v5.0 补齐了后端工程化（缓存、追踪、熔断）。但从**用户交互**角度看，知识卡片页面仍停留在"数据管理页面"层面，存在四个核心痛点：

| 痛点 | 影响 |
|------|------|
| 浏览和查找 | 卡片网格信息密度低，搜索能力有限，分组筛选不够灵活 |
| 复习体验 | 前端临时队列，无间隔重复调度，无复习统计，复习间隔无科学依据 |
| 创建和管理 | 工具栏拥挤，卡片无法快速预览，批量操作流程繁琐 |
| 整体交互感 | 单栏布局不够现代，缺少快捷操作，响应式适配粗糙 |

**目标**：将知识卡片从"数据管理页面"升级为"知识学习工具"——三栏布局 + SM-2 间隔重复 + 可展开卡片 + 复习统计。

## 三、方案 A — SM-2 间隔重复复习系统

### 3.1 数据模型

**新增表 `card_review_record`**：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT AUTO_INCREMENT | 主键 |

| repetition | INT NOT NULL DEFAULT 0 | 连续正确次数 |
| reviewed_at | DATETIME NOT NULL | 本次复习时间 |
| next_review_at | DATETIME NOT NULL | 下次应复习时间 |
| created_at | DATETIME DEFAULT NOW() | 记录创建时间 |

**knowledge_card 表新增 3 个冗余字段**（方便列表查询，避免 JOIN review_record）：

| 字段 | 类型 | 说明 |
|------|------|------|
| review_next_at | DATETIME NULL | 下次复习到期时间 |
| review_count | INT DEFAULT 0 | 累计复习次数 |
| last_reviewed_at | DATETIME NULL | 上次复习时间 |

### 3.2 SM-2 算法

用户评分映射：

| 按钮 | quality | 含义 |
|------|---------|------|
| 忘了 | 0 | 完全不记得 |
| 模糊 | 3 | 有印象但不确定 |
| 熟悉 | 5 | 轻松回忆 |

核心调度逻辑：

```
输入：quality (0/3/5), 当前 easiness_factor, interval, repetition

if quality >= 3:
    if repetition == 0 → interval = 1
    elif repetition == 1 → interval = 6
    else → interval = round(interval × easiness_factor)
    repetition += 1
else:
    repetition = 0
    interval = 1

easiness_factor = max(1.3, EF + 0.1 - (5 - Q) × (0.08 + (5 - Q) × 0.02))
next_review_at = now + interval 天
```

间隔递增示例（连续评"熟悉"5）：
- 第 1 次 → 1 天后
- 第 2 次 → 6 天后
- 第 3 次 → ~15 天后
- 第 4 次 → ~37 天后
- 第 5 次 → ~93 天后

### 3.3 复习队列调度

```
getReviewQueue(userId, groupId?)
  1. 查询用户所有 confirmed 卡片（可按 groupId 筛选）
  2. 分类：
     - review_next_at IS NULL → 新卡片 (newCards)
     - review_next_at <= now → 到期卡片 (dueCards)
  3. 合并：dueCards + newCards（到期优先）
  4. 对每张卡片查最新 review_record，组装 ReviewInfoDTO
  5. 返回 { cards, totalDue, totalNew }
```

### 3.9 面试 Trade-off

> **Q：为什么选 SM-2 而不是 Leitner Box 或其他间隔算法？**
> A：SM-2 是最经典的间隔重复算法（SuperMemo 1987），参数少（EF/interval/repetition 三个变量），效果经几十年验证。Leitner Box 是固定箱子模型，灵活度不如 SM-2 的连续 EF 调整。Anki 也基于 SM-2 变体。三个评分按钮（忘了/模糊/熟悉）简化了用户操作，覆盖核心调度路径。

> **Q：复习记录为什么要单独建表？**
> A：一张卡片可能有多次复习历史，如果只存最终状态在 knowledge_card 上会丢失历史轨迹。单独建表支持：1）复习日历统计（每天复习了几张）；2）连续学习天数计算（streak）；3）未来可能的复习曲线可视化。knowledge_card 上的三个冗余字段是为了列表查询不 JOIN，典型的空间换时间。

> **Q：knowledge_card 上冗余复习字段的数据一致性怎么保证？**
> A：提交复习答案时，`submitAnswer()` 在同一个事务里同时插入 `card_review_record` 和更新 `knowledge_card` 的 `review_next_at/review_count/last_reviewed_at`。事务保证原子性，冗余字段不会不一致。

### 5.6 面试 Trade-off

> **Q：卡片展开为什么选手风琴模式？**
> A：信息密度考虑。如果允许多卡片同时展开，长列表会变得非常长，用户需要大量滚动。手风琴模式保证展开的内容总是当前关注的焦点，视觉焦点清晰。同时实现简单：一个 `expandedId` ref 控制全部。

### 6.4 面试 Trade-off

> **Q：响应式为什么用 CSS 媒体查询而不是 Vue 的响应式库？**
> A：布局断点是纯视觉适配，CSS 原生媒体查询性能最好（无 JS 运行时开销），且与 Flex 配合自然。Vue 响应式库适合需要在 JS 层感知屏幕尺寸的场景（如条件渲染不同组件），本场景不需要。

```sql
CREATE TABLE card_review_record (
  id               BIGINT AUTO_INCREMENT PRIMARY KEY,
  card_id          BIGINT       NOT NULL,
  user_id          BIGINT       NOT NULL,
  quality          TINYINT      NOT NULL COMMENT '0~5',
  easiness_factor  FLOAT        NOT NULL DEFAULT 2.5,
  `interval`       INT          NOT NULL DEFAULT 0,
  repetition       INT          NOT NULL DEFAULT 0,
  reviewed_at      DATETIME     NOT NULL,
  next_review_at   DATETIME     NOT NULL,
  created_at       DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  INDEX idx_card_user (card_id, user_id),
  INDEX idx_user_next (user_id, next_review_at),
  INDEX idx_user_card_reviewed (user_id, card_id, reviewed_at DESC),
  CONSTRAINT fk_review_card FOREIGN KEY (card_id) REFERENCES knowledge_card(id) ON DELETE CASCADE
);
```
