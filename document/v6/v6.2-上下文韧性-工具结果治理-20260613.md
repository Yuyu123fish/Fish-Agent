# Fish-Agent v6.2 上下文韧性（工具结果治理 A+B+C）

> 日期：2026-06-13
> 主题：单工具结果预算 + 摘要 + 检索式注入（让单个工具结果再也吃不爆上下文）
> 状态：**已实施，经两轮审查通过**（mvn test 绿）
> 来源：虾皮 Q9-13「上下文过长 / 工具结果太长 / 上下文爆炸 / 日志超窗口」、头条「大上下文窗口场景」
> 关联：v5.3 ToolRegistry、v5.4 Token 预算、v6.1 Trace（记录处置方式）；面经驱动路线见 `temp/`

## 一、背景与动机

v5.4 有**总量预算**（`TokenEstimator` + `ContextBudgetAllocator` P0-P6 + `emergencyTrim` 兜底），但**单个工具结果无独立预算**——一个 log / FileRead 返 50KB 会先吃爆总量、再被 `emergencyTrim` 乱砍，且超长内容是"硬塞"而非"检索式注入"。虾皮一连串问"工具结果太长 / 上下文爆炸 / 日志超窗口"答不出系统解。本版让**单个工具结果封顶**，并给超大结果一条"分片 + 按需回取"的招牌路径。

## 二、设计原则

1. **A 兜底必做、B 中档按需、C 招牌**：三层递进，单结果 token 预算保证不爆总量。
2. **字符预算从 `TokenEstimator` 反推，绝不硬编码 `×4`**：CJK 约 1.5 字符/token、Latin 约 4 字符/token——项目主语言是中文，固定 Latin 比例会让中文结果绕过预算（首轮审查发现的核心 BLOCKER）。
3. **C 用 Redis scratch + 关键词检索 MVP**：不引入向量依赖，turn 结束 CAS 主动清，TTL 兜底。

## 三、方案与实施

### 3.1 A 单结果预算 + 智能截断（兜底）
`ToolResultBudgeter` 对每个工具结果封顶 N token（默认 4K）：**head + tail 保留**（头有 schema/状态码、尾有最新日志/结论），中间写 marker。字符预算 `initialCharBudget` 按文本样本经 `TokenEstimator` 采样反推 CJK/Latin 密度（clamp [1.0, 4.0]），再用 while 循环收敛到 token 上限——保证任何语言的单结果都不超预算。按工具可配 `budgetOverrides`。

### 3.2 B 结果摘要（中档）
`ToolResultSummarizer`：结果超"摘要阈值"（默认 8K）→ 走 `memoryChatModel` 忠实摘要（保留错误/数字/路径/URL/时间/结论），摘要仍受 A 封顶；模型不可用或失败自动回落 A，绝不影响工具主链路。

### 3.3 C 检索式注入（招牌）
真正巨量结果（超"scratch 阈值"默认 20K token）：**不截断、不摘要** → `LargeResultScratchStore` 按 turnId 分片（token-aware，每片收敛到 `scratchChunkTokens`）入单轮 scratch（Redis `fish:scratch:{turnId}` + TTL，Redis 不可用走进程内兜底）→ 只注入 top-k 预览 + 检索提示；并给 agent 一个 `search_large_result` 工具按关键词回取（带单轮调用上限防滥用，空 scratch 不计数）。

### 3.4 协同
- `ToolRegistry` 改为 **turn-bound 动态 callback**：有 turnId 的真实链路每轮重建工具集，把 scratch key、调用上限、TurnTrace 绑到同一轮；`wrap` 内 set/restore `TraceContext` 透传 turnId。
- `ChatService` 把 scratch 清理挂到 `ChatTurnLifecycle` 的 **CAS finish callback**——success / error / cancel / timeout 四路都清 `fish:scratch:{turnId}` + `:calls` 两 key。
- `TurnTrace.Node` 新增 `disposition`（truncated / summarized / retrieved），`TraceCollector.recordNode` 7-arg 重载，治理节点落 trace，可追溯"为什么这条只有片段"。
- A/B/C 产物最终都进 `ContextBudgetAllocator`——per-result 封顶 = 单结果吃不爆总量。

## 两轮审查

首轮发现 1 个 BLOCKER + 3 边界 + 3 取舍项：
- **BLOCKER（中文预算失效）**：`ToolResultBudgeter` 旧用固定 `budget×4`（Latin）算字符上限，而 `TokenEstimator` 对 CJK 是 1.5 字符/token → 中文结果落在 6K-16K 字符时，旧守卫 `head+tail >= text.length()` 直接返回**原文 unchanged**，既超预算、又因 disposition=unchanged **不留 trace**。全部测试是 ASCII（`"HEAD-"+x×2000`、`"error 500\n".repeat(500)`）故隐形。
- **B2 连带**：scratch 分片同样 `×4`，中文 top-k 预览可达 ~7200 tokens。
- **N1**：空 scratch 搜索也消耗调用配额；**N3**：marker 文案中英混搭（"已retrieved"）。
- **S1/S2/S3（取舍，非 bug）**：每轮重建 ReactAgent、`store` 非原子 load-add-save、B 摘要同步阻塞热路径。

全部修复：Budgeter 与 ScratchStore 改 **token-aware 字符预算（采样反推 + clamp）+ while 收敛**，删危险守卫（超预算绝不再返回 unchanged）；空搜索不计数；marker 中文化（截断/摘要/检索式注入）；补 4 条中文回归测试（**旧码必挂**）。二轮通过，残留仅"病态小预算（≈1 token）floor"——真实配置最低 4096 不可达，且即便触发也留 trace，不修。

## 六、面试 Trade-off

| 问题 | 回答要点 |
|---|---|
| 工具结果太长吃爆上下文怎么办 | A 单结果 token 预算头尾截断（兜底）→ B LLM 摘要（中档）→ C 检索式注入（招牌：超大结果不截断不摘要，分片入单轮 scratch，只注 top-k，agent 用 search_large_result 按需回取） |
| 为什么超大日志不直接截断/摘要 | 截断/摘要丢细节；C 把全文留 scratch、只注预览+检索提示，细节按需可回取，既不爆上下文又不丢信息 |
| scratch 为什么用 Redis 不用进程内 | 跨进程可见 + TTL 自动回收；进程内仅作 Redis 不可用兜底；turn 结束 CAS 主动清两个 key |
| 字符预算怎么定的（踩过的坑） | 最初按 Latin ×4 算，中文 1.5 字符/token 导致 6K-16K 中文结果绕过预算且无 trace；改成从自家 TokenEstimator 采样反推 CJK/Latin 密度 + while 收敛 |
| 每轮重建 agent 不贵吗 | turn 隔离换的构建成本，框架支持运行时工具上下文后可复用 graph（诚实取舍） |
| B 摘要同步调用会不会拖慢 agent | 会加一次 LLM 往返；按需触发 + 可 `summarize-enabled=false` 关，巨量结果仍走 C |
