## 背景：一次"知识图谱链路"对抗验证审计

起手不是写代码，是一次多 agent 并行深读 + 逐条对抗验证的审计：8 个组件并行深读知识卡片全链路（提取 / CRUD 缓存 / 关键词归一化 / 关联发现 / ES 双写 / RAG 召回 / DDL / Controller）→ 每条发现被独立 agent **重新打开代码核对**（5 条伪阳性被剔除，含一条数学自相矛盾的 token 估算指控）→ 跨组件完整性审查。产出 **40 条为真发现 + 6 条架构级**。

**最扎心的结论**：整套"知识图谱"精心建模了 `card_relation`(precedes / derived_from / contains / related) 与 `keyword_relation`，但 **RAG 召回阶段从不沿边遍历**——召回只做卡片/切片的文本 + 向量检索，图遍历能力为零。精心建模的关系类型在召回侧退化为装饰字段。这一条直接催生 B 线。

**贯穿全链路的反模式——静默失效**：embedding 失败写空数组污染 `dense_vector`、关联发现候选超 100 对时 embedding 信号整体置零、ES 写删失败仅 `log.warn` 无对账——与 memory `rerank-silent-failure-fix` **同源**。催生 A 线。

三项按 ① P0 → ② 图谱 → ③ trace 顺序落地，各自独立 spec→TDD→实现。

## A. P0 静默失效治理（embedding 空 / 候选置零 / ES 不一致）

**Situation**：三处静默失效让卡片在 RAG 里"消失得不留痕迹"——

1. `KnowledgeCardEsSyncService.embedForCardQuietly` 失败返回 `List.of()` → 空数组写进 `dense_vector` 字段 → ES 维度校验**拒收整篇文档** → 被 catch 吞掉 → **卡片在 ES 彻底不存在**（全文 + 向量都召回不到），方法注释却写着"保证全文能力"。
2. `CardRelationDiscoveryService` 候选对 `> 100` 时 embedding 评分直接 `Map.of()` 整体置零 → 越是大库、越需要语义区分的场景，S4 信号反而被关掉，且无任何日志。
3. ES 写/删失败仅 `log.warn` 吞掉 → MySQL 已 confirmed、ES 缺文档，**无重试 / 对账 / 补偿**，卡片永久消失且用户无感（前端列表走 MySQL 仍看得到，掩盖了问题）。

**Task**：失败要"**降级且留痕**"，不要"静默且丢弃"；给 ES↔MySQL 一致性兜底。改动小、是真 bug、还能当面试弹药（补 rerank 短板）。

**Action**：
1. **embedding 写 null**：`embedForCardQuietly` 两条失败路径返回 `null`（不再 `List.of()`）；Spring Data 的 `MappingElasticsearchConverter` 默认**省略 null 字段** → 文档正常落 ES、只是没有 embedding 字段 → 全文照常、kNN 自动跳过。`findSimilarConfirmed` 加 null 守卫。从"整篇丢失"变"优雅降级（仅向量路跳过）"。
2. **候选超预算降级补算**：抽纯函数 `selectEmbeddingScope`——候选对 `> 100` 时按其余三信号（关键词 Jaccard / 同组 / 关键词层次）降序取 top-100 对再算 embedding，并 `log.warn` 降级提示；头部候选保留 S4 信号，只有长尾丢失。注意：成本随**去重 anchor 数**走而非候选对数，原 `candidates.size()` 开关偏保守。
3. **ES↔MySQL 对账任务**：新增 `KnowledgeCardEsReconciliationService`（`@Scheduled fixedDelay=120_000`，镜像 `OrphanTaskCompensationService`）——回填缺 embedding / 缺失的 confirmed 文档 + 清孤儿；纯函数 `diffReconciliation` 做集合差分（`backfill = ES 缺 embedding ∪ (MySQL 有 ES 无)`，`orphan = ES 有 MySQL 无`）；ES 查询辅助（`listConfirmedCardIds` / `listConfirmedMissingEmbeddingCardIds`）放 `KnowledgeCardEsSyncService` 集中 ES 访问。

**Result**：
- embedding 失败从"整篇丢失"变"优雅降级"；大库不再整体丢 S4；ES↔MySQL 最终一致性有了兜底（对账能修任何来源的不一致：网络抖动 / ES 重启 / 吞异常）。
- **10 个新测试**（`KnowledgeCardEsSyncServiceTest` 4 + `CardRelationDiscoveryServiceTest` 2 + `KnowledgeCardEsReconciliationServiceTest` 2 + 2 个对账查询 helper 覆盖），全量 **270/270 绿**。
- 边界：`fish.card.es-reconcile.enabled`（`matchIfMissing=true`）可关；`BATCH=2000` 有界；本轮**不做 afterCommit 解耦**（对账已覆盖"提交成功 ES 失败"与"MySQL 回滚 ES 已写"两方向，afterCommit 属优化项）。

**代码**：`card/service/KnowledgeCardEsSyncService.java`（null embedding + 对账查询 helper）、`card/service/CardRelationDiscoveryService.java`（`selectEmbeddingScope` + `partialScore`）、`card/service/KnowledgeCardEsReconciliationService.java`（新）；测试 3 个类。

## B. 知识图谱接入召回 + 死代码清理

**Situation**：`card_relation`(precedes / derived_from / contains / related) 建表建索引、关联发现四信号投票持续产出边，但召回阶段零遍历——用户问"X 的前置概念是什么"，即便库里存在 `A precedes X`，召回也只命中 X 本体。另：`keyword_relation` + `keyword.parent_id` 表/实体存在、注释了 synonym/broader/narrower 语义，但**全工程零写入路径**——关联发现的 S3（关键词层次/关系）扩展恒为空集，是"建了不写"的灰色地带，文档却把它描述为核心能力。

**Task**：让精心建模的图关系**真正进入模型上下文**（precedes / synonym 不再是装饰字段）；清理死代码让代码不再撒谎（表/实体保留，供将来补写入路径）。

**Action**：
- **`CardGraphExpander`**（新，`rag.pipeline.recall`）：精排后的 expand 阶段，对召回命中的卡片沿 `card_relation` 取 **1 跳邻居**，按关系类型加权（`precedes` / `derived_from` / `contains` = 0.9 ＞ `related_to` = 0.6），与已命中卡片去重、按「种子分 × 权重」排序、截断上限 4，以来源标注**「图谱」**注入。邻居**故意绕过精排**——它的相关性来自与种子的图关系，而非与查询文本的匹配（与 `ContextExpander` 加 chunk 邻块同理）。核心逻辑放 package-private `expand(hits, userId)` 便于单测（绕过 `UserContextHolder` 线程本地）。接入 `RagRecall.DefaultAugmentation` 的 expand leg（`cardGraphExpander.expand(contextExpander.expand(provenance))`）+ `RagRecallConfiguration`（注入 `CardRelationMapper` / `KnowledgeCardMapper`）。
- **删死代码**：`CardRelationDiscoveryService.buildExpandedKeywordMap` 里读 `keyword_relation` / `parent_id` 的恒空分支删掉，移除 `keywordRelationMapper` 字段；S3 信号诚实为 0。`keyword_relation` 表 / `KeywordRelation` 实体 / `KeywordRelationMapper` 类**保留**（将来补概念分类写入路径即可），代码不再读恒空结构。

**Result**：
- `precedes` / `derived_from` / `contains` / `related` 等关系类型从详情页装饰字段，变成召回阶段真正消费的图遍历能力——知识图谱名副其实。
- `CardGraphExpanderTest` 4 条（加权打分 / 去重 / 截断 / 无种子直通），全量 **276/276 绿**。
- 边界：邻居在 top-K 命中后取（K 小，`selectRelationsForCard` 每 seed 一次，调用数有界）；未做多跳（YAGNI）；真实 DB 图遍历行为待集成验证。

**代码**：`rag/pipeline/recall/CardGraphExpander.java`（新）、`rag/pipeline/recall/RagRecall.java`（`DefaultAugmentation` 接线）、`rag/pipeline/recall/RagRecallConfiguration.java`（注入两个 mapper）、`card/service/CardRelationDiscoveryService.java`（删死分支 + 移除字段）。

## C. per-fact trace（可衡量性地基）

**Situation**：trace 只记聚合计数（`recall_total_hits` / `injected_fact_count` / 各段 latency），**不记每条注入事实的来源 / 命中 id / 分数**。后果：关联发现的 false-positive 率不可知、卡片召回被采纳率不可知、B 线新引入的图谱邻居有没有实际帮上忙不可观测。**不可衡量 = 不可改进**——A/B 线的修复都无法回归验证。直击 v6.1 eval/trace 路线在图谱子系统的缺口。

**Task**：把"这一轮到底注入了哪些事实、各自来源（记忆 / 用户 / 图谱 / 公开）、分数多少"落 trace，为离线 eval 打地基。**无 DB 变更**。

**Action**：
- `RagTraceDocument` 加 `injected_facts`（ES object：`id` / `source_label` / `score`）+ 内嵌 `InjectedFact`；`RagQualityLogger.traceMapping()` 补对应 mapping。
- `RagQualityLogger.toInjectedFacts(List<RecallHit>)` 纯函数把 `finalHits` 映射成明细（已单测）。
- `RagRecall.doBuildAugmentation` 注入完成后落 `trace.setInjectedFacts(...)`。

**Result**：每轮 RAG trace 现在能回答 per-fact 溯源；图谱邻居以 `source_label=图谱` 出现，可观测、可评估。`RagQualityLoggerTest` 2 条（映射 + 空值），无回归。

**代码**：`rag/tracing/RagTraceDocument.java`（+`InjectedFact` / `injected_facts`）、`rag/tracing/RagQualityLogger.java`（`toInjectedFacts` + `traceMapping`）、`rag/pipeline/recall/RagRecall.java`（落 trace）。
