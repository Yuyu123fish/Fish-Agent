## 一、v2.4 一句话增量

1. **独立记忆模型**：`fish.memory.chat.*` 配置专用 `ChatModel` Bean（`memoryChatModel`），`MemoryCompressionService` / `LongTermMemoryIngestionService` 通过 `@Qualifier` 注入；**DEEPSEEK** 下用 `OpenAiChatModel.builder(主模型).defaultOptions(...)` 复用同一 OpenAI 客户端栈；**DASHSCOPE / OLLAMA** 当前阶段降级为与主对话相同模型。  
2. **会话级互斥**：`POST /api/chat/stream` 在 `ChatService` 内对 `fish:mutex:session:{sessionId}` 执行 **`SET NX EX 120`**；失败返回 **HTTP 409** + `{"code":"SESSION_LOCKED",...}`；释放与 **v2.3 SSE 槽位 DECR** 合并为同一 `releaseSseSlotOnce`（**须先于抢锁创建 Runnable**，锁失败时先 `run()` 再抛异常，避免 SSE 泄漏）。  
3. **孤儿任务补偿**：`OrphanTaskCompensationService` 每分钟扫描 `document_metadata.status=PROCESSING` 且 `updated_at` 早于阈值（默认 10 分钟）的记录，按 `KnowledgeManageService` 同语义 **ES delete_by_query**，再将行更新为 `FAILED` / `error_msg=worker timeout`；可通过 `fish.knowledge.compensation.enabled` 关闭。  
4. **Worker 幂等**：`elasticsearch.py` 新增 `delete_by_doc_id`，`processor.py` 在 **`index_name` 确定之后**、**bulk 写入之前**调用，避免 XAUTOCLAIM 重投时 chunk 数量变化导致 ES 脏残留。

## 二、记忆链路独立模型

### 2.1 动机

主对话（ReAct）与记忆任务（摘要压缩、长期事实抽取）原共用 `@Primary ChatModel`，无法单独指定更小/更便宜的模型或不同 temperature。v2.4 将记忆链路收敛到具名 Bean **`memoryChatModel`**，主对话逻辑（`ChatAgent`）不变。

### 2.2 配置（`fish.memory.chat`）

| 配置项 | 默认值 | 环境变量 | 说明 |
|--------|--------|----------|------|
| `enabled` | `true` | `MEMORY_CHAT_ENABLED` | `false` 时 `memoryChatModel` 即主模型引用 |
| `model` | `deepseek-chat` | `MEMORY_CHAT_MODEL` | DeepSeek 路径下独立 options 的模型名 |
| `temperature` | `0.1` | `MEMORY_CHAT_TEMPERATURE` | 摘要/抽取宜偏低 |

### 2.3 实现要点

- **`lombok.config`**：`lombok.copyableAnnotations += Qualifier`，使 `@RequiredArgsConstructor` 构造器带上 `@Qualifier("memoryChatModel")`。  
- **`FishChatModelConfiguration#memoryChatModel`**：Spring AI **1.1.4** 无 `(OpenAiApi, Options)` 双参构造，使用 **`OpenAiChatModel.builder(模板).defaultOptions(opts).build()`** 保留 ToolCalling / Retry / Observation 等与主模型一致的行为。  
- **未改动**：`ChatAgent`、主路由 `fishPrimaryChatModel`、`FishLlmEnvironmentPostProcessor`。

## 三、会话级并发互斥

### 3.1 与 v2.3 的关系

| 维度 | v2.3 | v2.4 |
|------|------|------|
| 粒度 | 每 `userId` SSE 并发上限 | 每 `sessionId` 互斥 |
| 目的 | 防用户开太多路流 | 防同会话双击发送导致历史/落盘竞态 |
| Key | `fish:ratelimit:sse:{userId}` | `fish:mutex:session:{sessionId}` |

两者叠加：先过拦截器令牌桶 + SSE INCR，再在 `ChatService` 抢会话锁。

### 3.2 Redis 与 fail-open

- **`RateLimitService#tryAcquireSessionLock` / `releaseSessionLock`**：`SET NX EX 120`，释放时 `DEL`。  
- **Redis 异常**：获取锁返回 **true**（放行），与限流 fail-open 一致。  
- **为何不在拦截器**：`sessionId` 在 **请求体**，`preHandle` 不便解析 body。

### 3.3 HTTP 409

仅 **`SessionLockedException`** 在 **`ChatController`** 中 **re-throw**，由 **`GlobalExceptionHandler`** 返回 JSON：

```json
{
  "code": "SESSION_LOCKED",
  "message": "此会话正在处理中，请等待回复完成后再发送"
}
```

### 3.4 SSE 槽位与锁释放顺序（重要）

`RateLimitInterceptor` 已对 **`POST /api/chat/stream`** 执行 SSE **INCR**。因此 **`releaseSseSlotOnce` 必须在 `tryAcquireSessionLock` 之前定义**；若抢锁失败，须先 **`releaseSseSlotOnce.run()`**（内含 DECR + 删锁 key 或仅 DECR——此时锁未获得则 DEL 无害），再 **`throw SessionLockedException`**，否则 SSE 计数泄漏。

## 四、孤儿任务补偿与 Python 幂等

### 4.1 问题背景

Worker 在 **ES bulk 之后**、**MySQL `SUCCESS` 之前**崩溃时：`document_metadata` 可能长期 **`PROCESSING`**；若消息被 **XAUTOCLAIM** 重投且 chunk 数变化，仅依赖 `_id` 覆盖无法删除「多出来的旧 chunk」。

### 4.2 Java：`OrphanTaskCompensationService`

- **`@Scheduled(fixedDelay = 60_000)`**：每分钟一轮；方法内外层 **try-catch**，单轮失败不拖垮调度。  
- **查询**：`status = PROCESSING` 且 `updated_at < now - timeoutMinutes`（默认 10，**`fish.knowledge.compensation.timeout-minutes`**）。  
- **ES**：与 **`KnowledgeManageService#deleteEsChunks`** 相同分支（PRIVATE：user-knowledge + legacy fish-user-memory `source_type=document`；PUBLIC：public-knowledge）。  
- **MySQL**：`UPDATE` 为 **`FAILED`**，`error_msg = worker timeout`**。  
- **开关**：**`fish.knowledge.compensation.enabled`**（默认 true）；`false` 时 **`@ConditionalOnProperty`** 不注册该 Bean。  
- **调度开关**：**`SchedulingConfiguration`** 上 **`@EnableScheduling`**（全局启用；仅补偿服务受 compensation 开关控制）。

### 4.3 Python：`delete_by_doc_id`

- 在 **`index_name` 赋值之后**调用 **`delete_by_query`**：`term doc_id = task_id`，`refresh=True`，`conflicts=proceed`。  
- 失败 **打日志不中断**整条流水线（与 Java 侧「尽力清理」风格一致）；若需强一致可后续改为抛错。

## 八、明确边界（本版本不做）

- 不为记忆链路单独引入新的 Spring AI **starter** 依赖。  
- 不在网关层或拦截器层解析 body 做会话锁。  
- **DASHSCOPE / OLLAMA** 下独立记忆模型仍为「降级主模型」，后续可扩展。  
- 前端未强制处理 409（可后续在 `chat.ts` 统一提示「会话处理中」）。
